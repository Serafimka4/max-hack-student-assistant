# Архитектура

## Общая схема

```
MAX (мобильный и веб)
 ├── бот @t475_hakaton_max_bot ──── вебхук ──┐
 └── мини-приложение (кнопка бота) ──────┐   │
                                         ▼   ▼
                         ┌──────────────────────────────┐
                         │ Laravel 13 (FrankenPHP)      │
                         │  /app      мини-приложение   │  Livewire 4 + Tailwind 4
                         │  /admin    админ-панель      │  Filament 5
                         │  /api/v1   API интеграций    │  Sanctum + Scramble
                         │  /max/webhook события бота   │
                         └───────┬───────────┬──────────┘
                                 │           │
                          очередь + планировщик   PostgreSQL 17
```

Одно приложение обслуживает три интерфейса. Мини-приложение и админ-панель не ходят в собственное API по HTTP: все три вызывают один слой предметной логики, поэтому правила совпадают.

## Слои

| Каталог | Назначение |
|---|---|
| `app/Actions` | Предметные действия: подача и отзыв заявки, решение по заявке, обращения, попытки теста, проверка практики, версии тестов и шаблонов |
| `app/Policies` | Права участников организаций; вызываются и из API, и из админ-панели |
| `app/Support` | Учебный календарь, профиль и сопоставление навыков, проверка данных запуска MAX, клиент API бота |
| `app/Livewire/MiniApp` | Экраны студента |
| `app/Filament` | Кабинеты организаций |
| `app/Http/Controllers/Api/V1` | REST API |
| `app/Notifications` | Уведомления через бота MAX |

Нарушение предметного правила — исключение `DomainRuleException`: API отвечает 422, интерфейсы показывают сообщение.

## Роли и доступ

Организация имеет тип «вуз» или «работодатель». Пользователь состоит в организации с ролью:

| Роль | Что доступно |
|---|---|
| Администратор | Всё в своей организации |
| Координатор | Заявки, обращения, каталог практик; в кабинете работодателя — отметка интереса к кандидату |
| Редактор | Тесты, шаблоны документов, частые вопросы, каталог практик |
| Проверяющий | Проверка практических заданий по тестам своей организации |

Студент связан с вузом отдельной записью: мини-приложение доступно только участникам пилота. На время пилота новые пользователи MAX привязываются к вузу из `MINIAPP_ENROLL_ORGANIZATION`.

Разграничение, на которое опирается сценарий:
- работодатель видит отклик и результаты диагностики, только если студент разрешил это при подаче заявки;
- проверяющий не видит имени студента — только номер попытки, и не может проверять собственное решение;
- обращение видят автор и сотрудники его вуза: режим конфиденциальный, не анонимный, и это написано в форме;
- правильные ответы на вопросы теста не покидают сервер.

## Модель данных

| Область | Таблицы |
|---|---|
| Организации | `organizations`, `organization_user`, `students`, `skills` |
| Расписание | `study_groups`, `lessons` |
| Контент | `faq_items`, `faq_feedback`, `document_templates`, `document_template_versions` |
| Практики | `internship_offers`, `internship_offer_skill`, `internship_applications`, `application_status_changes`, `employer_interests` |
| Диагностика | `assessments`, `assessment_versions`, `assessment_questions`, `assessment_attempts`, `attempt_answers`, `skill_results` |
| Практическое задание | `practical_submissions`, `practical_reviews` |
| Поддержка | `tickets` |

Все содержательные записи связаны с организацией — это основа переноса на другой вуз: меняются данные и настройки, а не сценарий.

## Версионирование тестов

Тест состоит из версий. Опубликованная версия неизменяема: правка создаёт новую версию, которая наследует правила оценки. В версии хранятся вопросы с привязкой к навыкам, текст практического задания, рубрика проверки и пороги:

| Правило | Где задаётся |
|---|---|
| Порог базового уровня по навыку | `basic_threshold`, по умолчанию 60% |
| Минимум вопросов на навык | `min_questions_per_skill`, по умолчанию 2 |
| Порог «Прикладного» по практике | `applied_threshold`, по умолчанию 70% |
| Порог «Уверенного» по практике | `confident_threshold`, по умолчанию 90% |

## Как считается результат

1. Вопрос засчитывается только при полном совпадении ответа с ключом; частичных баллов нет.
2. Балл по навыку — сумма полученных баллов к сумме максимальных по вопросам этого навыка.
3. Меньше `min_questions_per_skill` вопросов по навыку — «недостаточно данных». Это не низкая оценка.
4. Балл не ниже `basic_threshold` даёт «Базовый» уровень.
5. Практическое задание проверяет человек по рубрике. Оно повышает уровень только там, где базовый подтверждён вопросами: иначе хорошей практикой можно было бы перекрыть проваленную теорию.
6. Грейд: «Начальный» — базовый хотя бы по одному навыку; «Стажёр» — по всем навыкам версии; «Junior — предварительно» — после проверки практики прикладной уровень или выше по всем навыкам. Уровни middle и senior короткая диагностика не присваивает.
7. Незавершённая попытка не публикуется как итоговая оценка. История проверок сохраняется, пересмотр отмечается отдельно.

## Учебный календарь

Чётность недели считается от `MINIAPP_SEMESTER_START`: нечётная неделя — числитель. Пара «сейчас» определяется по часовому поясу `MINIAPP_TIMEZONE`. У группы хранятся источник расписания и время последнего обновления — они показываются студенту.

## Надёжность

- Повторная подача заявки не создаёт дубликат: на пару «предложение — студент» одна запись, отозванную заявку можно подать заново.
- Переходы статусов заявки заданы явно; отказ требует причины, она видна студенту.
- Уведомления идут через очередь, сбой отправки только логируется.
- Загрузка версии шаблона и создание версии теста выполняются в транзакции с блокировкой, поэтому номера версий не дублируются.
- Файлы шаблонов отдаются по временной подписанной ссылке: в MAX скачивание идёт через `WebApp.downloadFile`, куда сессия не передаётся.
